## Technical Context

Next.js/React/TypeScript frontend, Go HTTP/application/domain services, PostgreSQL JSONB confirmations/estimates and stored drawing bytes. Gemini/Ollama implement `Analyzer`; candidates currently contain rooms, doors/windows, room bounds, and engine/timing metadata. Openings have no evidence region/page. Estimates accept finish rates and manual exchange metadata, but do not store raw-material recipes, offers, or a direct confirmation-revision field. Do not assume those proposed fields/APIs already exist.

Repo app root is `ai-quantity-surveyor/` within the Git repository. Render Docker contexts target that folder. Web build uses `NEXT_PUBLIC_API_URL`; runtime uses `PORT` and `HOSTNAME=0.0.0.0`. API uses Neon `DATABASE_URL`, `ALLOWED_ORIGIN`, and provider environment variables. Hosted deployment was reported successful, not independently certified for private customer data or persistent background jobs.

## Constitution Check

- Preserve AI candidate -> human confirmation -> deterministic QS calculation. Model geometry cannot feed calculations.
- Constitution 1.5.0 approves informational feature extraction and separate paint/tile material formulas. Supplier price lookup is a narrowly bounded exception to the supplier exclusion, not procurement approval; region/source gates still apply.
- RAG/agent frameworks, structural trades, external works and multi-floor remain deferred under the ratified constitution.
- Authentication/access protection is an explicit release decision, not permission to invent users/roles or expose all drawings publicly.

## Technical Decisions

### Selected Page and Provider Input (FR-002, AC-03)

Add a page-preparation boundary owned by the Go analysis layer. Use the maintained Poppler utilities (`pdfinfo` for metadata and `pdftoppm` for selected-page PNG rendering), packaged in the API runtime image. This is one new OS dependency, not a new AI/agent framework; verify package availability, distribution-license obligations and resource behavior during implementation. Keep the browser's existing PDF.js for page browsing/selection only; the analysis evidence/review uses the canonical server image.

Add a page-count metadata endpoint and an analysis-bound page-image endpoint, defined in `contracts.md`. For a PDF, the new UI requires explicit selection before analysis. Omitted page from legacy API clients means page 1 and is recorded as `legacy-default`; it never authorizes processing the full document. Images use page 1. Reject out-of-range pages before contacting a provider. Render only the selected page, account for rotation/crop, and assign a SHA-256 digest and canonical pixel dimensions to that image. Send the same PNG to Gemini/Ollama, persist it once per completed preparation, and display it in review. Provider-relative page 1 is rebound by the server to the original page number. Do not use the current PDF regex-based aspect helper for these new analyses.

Initial rendering limits: original file <= existing 10 MB, output long edge <= 3000 pixels, derived image <= 10 MB, metadata deadline 5 seconds, render deadline 20 seconds, one render process per API instance. Invoke fixed executable/argument arrays with `exec.CommandContext`, never shell interpolation; use private temporary directories and remove them on every exit. Bound stderr/stdout and process/page allocations; treat encrypted/unreadable/resource-exceeding files as named retryable preparation failures where applicable. A 3000-pixel image may still miss small text: benchmark fixture accuracy before changing limits, never claim the approved thresholds are achieved merely by this choice.

Preserve original uploaded bytes. Source metadata is server-owned and copied into confirmations. Historical records without trustworthy source metadata display unknown provenance; do not infer a page from the current browser selection. A new selected page produces a new analysis; old revisions remain discoverable but cannot supply the new page's preview.

### Candidate, Review and Confirmation (FR-001-005, FR-015)

Keep `Analyzer.Analyze` as the provider boundary by passing prepared PNG bytes and a PNG filename; provider prompts gain optional per-field evidence and informational `features`. Define `source`, `evidence`, `reviewIssues`, and manual correction records additively as in `contracts.md`. Server candidate validation permits nullable required measurements when accompanied by uncertainty, but checks structural IDs/types, finite confidence, coordinate range and room associations. Required numeric confirmation validation remains strict. Invalid optional evidence is excluded from highlighting with a named review issue; it cannot silently change a measurement.

Use three separate client states: immutable original candidate, editable pending review and immutable latest confirmed revision. `step-review.tsx` integrates a responsive split/unframed drawing and dimension panel; `drawing-view.tsx` gains canonical-image input, bounded zoom/pan, linked room/opening/field selection and list fallback. Do not add another review wizard or independent layout confirmation. Render pending dimension text only as labels/panel values, not as geometrically inferred measurements. Settings-derived height stays visibly assumed. Confirmation response updates the confirmed snapshot only after server validation/persistence succeeds; estimate recalculation remains separate.

Server derives correction records by comparing original and submitted values; clients cannot replace engine identity, source digest or original evidence. Manual evidence marks are tagged `manual`, validated against the canonical image, and never imply engine corroboration. Missing source regions allow textual numeric review. Stairs/balconies remain excluded from `estimate.confirmedPlan` and `domain.Calculate`.

### Exact Estimate Provenance and Material Budgets (FR-006-007)

When creating a new estimate, read one immutable confirmation snapshot, calculate from that snapshot, and persist additive `sourceConfirmationRevision`, `sourceFloorPlanId` and `sourcePageNumber`/digest when known. Validate project ownership explicitly; current estimate lookup must not allow a foreign project's estimate via ID fallback. Do not calculate from latest data and fetch a revision later, as concurrent reconfirmation could mislabel the result. Existing QS formulas, totals, rate inputs and old exports remain unchanged.

Put pure paint/tile formulas in a neighboring `api/internal/domain/materials.go` with focused tests. Use one `api/internal/materials` application/persistence boundary for budgets, curated products/offers and comparisons, rather than introducing separate frameworks or supplier-management services. Reuse PostgreSQL access and existing common HTTP errors; use in-memory repositories for unit tests. Newly created records commit before publishing a success response; version allocation uses transactions/unique constraints, not process-local list length. Historical estimates without the exact confirmation revision return `SourceRevisionUnavailable` for budgeting and remain viewable/exportable; request a new confirmed estimate instead of inventing a backfill.

For material formulas only, normalize source measured areas and reviewed numeric recipe inputs to six decimal places, using round-half-away-from-zero, then perform exact decimal-rational operations using the Go standard library (`math/big.Rat`). This explicitly versioned material precision does not round/change the existing QS result. Apply waste once, aggregate only identical recipe/product groups, then compute whole packs using exact quotient/remainder ceiling. Display two-decimal amounts without rounding intermediate costs; currency amounts use explicit minor-unit rounding at basket total. Compare thresholds and test values at exact pack boundaries and just above/below the material precision boundary. Formula version `finish-materials-v1` records this policy.

**A3 resolution:** Validate field constraints both before and after normalization, before any division. Normalized coverage/pack amount must be >0; reject raw positive values rounding to zero with a named field error, never clamp to a minimum. The normalized representable minimum is `0.000001` of the declared unit. Zero excluded quantities stay zero, but positive areas rounded to zero are rejected as unsupported precision rather than producing zero packs. Apply the same guard to imported products and offer-specific recalculation. Tests include raw `0.00000049`, `0.00000050` and `0.00000051`, exact pack boundaries and ordinary AC-04 inputs.

**A2 resolution:** Budget service validates uniqueness of `(roomId, trade)` before loading/aggregating material allocations. Duplicate paint/wallTile/floorTile allocations for the same room return a named 400 error with no saved version. All amounts come from the frozen confirmed estimate. Only validated distinct-room allocations with identical reviewed recipes/products can share packs; caller group labels cannot force incompatible products together. Split-area/multiple-product allocation within one room/trade is outside this demo. Existing numeric confirmation remains sufficient; no new confirmation screen is introduced.

### Colombo/LKR Fixture Catalog (FR-008-013)

Start with versioned JSON fixture/import files loaded by an operator-controlled command; no customer refresh endpoint or web scraper in this demo slice. Fixture supplier names are fictional and clearly labeled. Imports from real catalogs require provenance and authorized use; synthetic offers never use real supplier URLs to suggest a quotation. No runtime HTML-parser dependency is added until a permitted source is selected.

Group products by reviewed application/specification: paint interior wall use, finish and coverage basis; tiles wall/floor use, material, dimensions, grade and pack coverage. Brand variants can be compared only under a reviewed equivalence key and still disclose their differences. Budget/standard/premium labels remain disabled until the criteria are defined. The importer validates positive prices/pack sizes, LKR or explicit foreign currency, source timestamps and nullable availability/charges. Default freshness for the fixture/import pilot is 24 hours; fixtures remain labeled synthetic regardless of age. A supplier-specific approved validity overrides this only after documented policy review. Expired, unavailable or incomplete offers remain viewable with warnings but are not ranked as a verified cheapest delivered option.

Location filter is country `LK`, city `Colombo`, optional postcode; no browser geolocation service or distance-based delivery inference is required for the first implementation. Optional consented geolocation can prefill a reviewed location, never approve coverage. LKR is the comparison currency; prefer LKR fixtures. Foreign offers require an explicit positive user-reviewed rate, base/quote pair and timestamp before joining an LKR comparison; otherwise keep them separate. Existing USD-base QS estimation is not modified.

Recompute requirements per offer if pack size or reviewed coverage differs. Count delivery once per supplier branch basket using declared rules; unknown conditions keep the delivered total null. Save selected observation values, product/recipe/quantity/charge/conversion metadata and formula version in an immutable comparison linked to an immutable budget. Refresh adds observations, not updates to saved comparisons. Export a separate XLSX workbook using existing Excelize with Requirements, Offers, Sources and Assumptions sheets; no changes to the existing QS workbook.

**A1 resolution:** Add a budget-scoped POST comparison-preview route that loads frozen quantities, accepts bounded alternative baskets of immutable observation IDs and returns per-offer packs/material costs, basket tax/delivery and incomplete-total warnings without writes or network collection. Use the same pricing function for preview and Save. Explicit Save recomputes against the selected observations under current eligibility/freshness, never trusts client totals or substitutes a newer offer silently. An expired/unavailable selection returns 409 and requires renewed review; a successful Save creates one immutable comparison version. UI shows alternatives before any Save action.

### Hosted Processing and Access (FR-014)

Retain Render/Neon deployment. Cap provider concurrency at two and PDF rendering at one per instance; reject excess new work with 429 and a retryable message. Persist preparation/analysis state before provider invocation. Recover only expired leased jobs as defined below; never fail another instance's live work simply because an instance started. No durable job queue is promised. Provider timeouts/cancellation cover all stages. Preserve reusable canonical page images but do not assume an in-memory job will survive sleep/redeploy.

**A4 resolution:** Store unique worker `ownerId`, per-claim `attemptToken`, `leaseExpiresAt` and `heartbeatAt` in job-control columns. Initial lease is 60 seconds, renewed every 15 seconds using database time. Every renewal, source publish and terminal write is conditional on matching owner/token, `Analyzing` state and lease not expired. On lost renewal, cancel provider/render work and discard late results. Startup plus bounded periodic reclamation conditionally fails only expired leases, without redispatch; another replica's unexpired job is untouched. Legacy jobs without ownership metadata require explicit review/fresh analysis, not an invented lease. Test overlapping rollouts, lost heartbeat, expired owner and old-process completion after recovery.

**A6 resolution:** Add persistent daily usage counters and reservation records keyed by shared configured quota namespace/provider/UTC date. Configure per-provider daily limits below the applicable account allowance; missing/zero limits disable dispatch. After successful preparation, reserve quota atomically immediately before each outbound call/retry while checking the live job lease. Idempotent reservation identity must not authorize duplicate sends; automatic HTTP replay/redirect retries are disabled. All reserved attempts remain consumed conservatively, including failed requests or pre-send crashes; no automatic refunds. Use database UTC day buckets, so midnight starts a new bucket without erasing audit history. Before acceptance, quota exhaustion returns 429/reset `Retry-After`; after 202 it is persisted as a structured analysis failure with UTC `retryAt` for polling. Store unavailability always fails closed. Quotas are shared across replicas, additive to concurrency and not a monetary spending cap. No provider key is stored in usage keys/records.

**Async response clarification:** Run request/reference/page/capacity/configuration preflight and persist an owned job before 202. Immediate failures use normal HTTP errors. After 202, render/quota/provider failures use fenced `AnalysisFailed` persistence; successful status polling is HTTP 200 with additive structured error/retry/reset metadata and legacy `errorMessage`, not a delayed error on the accepted POST. A quota precheck is advisory only; a reservation race after preparation never dispatches and becomes a polling failure. If DB outage prevents terminal persistence, cancel work and report temporary status-store errors until recovery can record a failed/interrupted job under valid ownership/expiry rules. Frontend polling helpers show the failure/retry information without discarding saved inputs. T044/T055/T009/T016 cover both phases.

Initial release posture is sample-only on the current public app, with bounded provider calls and no real customer drawings/precise location records. This does not make the unauthenticated API safe for confidential data. Confidential release is blocked until a managed gateway/access mechanism protects both frontend and all API/drawing/export/provider routes and is verified; do not quietly introduce user/role management. Source approvals, freshness policy for real catalogs and access selection remain T004/T005 gates. Previously exposed credentials must be rotated outside chat.

## Persistence and Security

Use additive optional candidate fields and dedicated versioned product/offer/budget records; avoid overwriting historical JSONB payloads. Persist original candidate plus user corrections and server-owned source provenance. Store price observations separately from current refresh status, and copy selected offer values into snapshots.

Keep credentials in hosted environment settings only; rotate any previously shared keys. Allowlist supplier domains and redirects, reject private/link-local targets, bound response size/time, and prevent SSRF. Treat supplier content and drawing text as untrusted data, not instructions. Require explicit source-policy approval; stop a source that becomes disallowed.

Location data is minimized. Protect web AND API (including drawing/export routes and provider calls); decide a managed gateway/app-level mechanism before private-data release. Until then use isolated sample data, provider-call limits and an explicit demo restriction. Free hosting/data quotas and third-party AI usage are not unlimited or guaranteed zero-cost.

## Verification Strategy

- Annotated fixtures: approved AC-10 set/thresholds, missed/extra windows, repeated symbols, uncertain dimensions, stairs/balconies, selected/rotated page mapping, missing bounds, provider omissions, and room/dimension regression. Report measured precision/recall separately for each provider/model, not self-reported AI confidence.
- Domain fixtures: AC-04, finite/positive coverage validation, coat count, pack boundary rounding, excludes, consistent units, single waste application, and unknown charges/currencies.
- API/persistence: cross-project/revision/page rejection, legacy records, immutable snapshots, source approval enforcement, failed refresh, restart recovery and export parity.
- Browser: AC-11 dimension preview/explicit confirmation, pending edits vs immutable prior values, units/assumptions, selected-page changes, zoom/pan, missing evidence/renderer fallback, manual feature correction, no geolocation permission, stale/quote-only offers, incomparable products and mobile overflow. Existing confirmed-input QS/Excel golden results remain identical.
- Supplier adapters use recorded permitted fixtures in automated tests, not flaky live sites; approved live smoke checks are a separate release gate.

**A5 resolution:** Evaluate raw AI output before human corrections with independent detection, dimension and localization reports on the same frozen set. Detection uses fixed identity/type/association matching, not a mandatory box. Dimensions require correct associated entity/unit and <=2% relative error across every legible label; missing/wrong association fails. Localization uses same-type one-to-one IoU >=0.5; missing/invalid regions fail this metric for new evidence-capable output, not automatically detection. Duplicate/unmatched/ambiguous predictions remain in denominators under rules frozen before tuning. Legacy missing location support is `notSupported`; do not fabricate boxes or misreport all detected windows as detection misses. Report unsupported legacy feature types separately.

Preserve AC-10 numeric thresholds for new detection/localization and dimensions. Compare fewer window detection misses/no worse room-dimension accuracy only for metrics supported by baseline and new output; report preprocessing/page/input representation and per-provider/model versions. Human-confirmed inputs validate the calculation workflow independently, never inflate raw AI accuracy. Illegible labels are reported separately without removing difficult legible cases after seeing output. Fixtures are not yet acquired and no target attainment is claimed.

Run behavior checks per slice before broader gates: preparation/page mapping -> candidate parsing/confirmation -> dimension-preview E2E -> exact provenance/material formulas -> persistence -> fixture comparison/export. Required pre-demo gates are `go test ./api/...`, `go vet ./api/...`, frontend typecheck/lint and existing/new Playwright workflows with PostgreSQL. Benchmarks include Render-equivalent 512 MB rendering/provider load, startup failures and cold-start handling. `quickstart.md` provides the planned commands and smoke sequence; no tests were run as part of this documentation-only planning pass.
